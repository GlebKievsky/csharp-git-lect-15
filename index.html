РАЗДЕЛ 01

Зачем это всё: два человека и один вордовский документ

Ветки нужны, чтобы работать параллельно и не мешать друг другу. Merge и rebase нужны, чтобы потом собрать эту работу в одно целое. Проще всего понять это на примере обычного Word.

Аня и Боря вдвоём пишут отчёт. Есть общий файл «Отчёт.docx» с двумя абзацами. Чтобы не мешать друг другу, каждый делает себе копию и работает в ней:

  • Аня дописывает текст после первого абзаца, потом ещё немного. У неё получаются версии «Аня v1» и «Аня v2».
  • Боря в это же время дописывает текст после второго абзаца. У него «Боря v1» и «Боря v2».

Теперь нужен один итоговый документ, где есть правки обоих. Вручную это больно: открыть два файла, сравнить построчно, перенести куски и ничего не потерять. А если Аня и Боря исправили одно и то же предложение по-разному — чей вариант оставить?

Git делает эту работу за нас. Вот как слова из мира Word превращаются в термины Git:

В мире WordВ мире Git
Исходный файл «Отчёт.docx»Коммит, от которого всё началось (общий предок)
Своя копия у Ани и у БориВетка: anya, borya
«Сохранить новую версию»Коммит
Собрать итоговый документ из двух копийMerge (слияние)
Боря берёт свежую версию Ани и заново вносит свои правки поверх неёRebase (перебазирование)
Оба исправили одно предложение по-разномуКонфликт: Git спросит тебя, какой вариант оставить
Запомни

Ветки — чтобы не мешать друг другу. Merge и rebase — чтобы потом собрать всё вместе.

РАЗДЕЛ 02

Быстрое повторение: коммит, ветка и HEAD

Без этих трёх понятий merge и rebase кажутся магией, а с ними становятся очевидными.

Коммит — снимок (фотография) всего проекта в какой-то момент. У него есть уникальный номер — хеш, например 8e3f1b4, — сообщение и ссылка на предыдущий коммит, то есть на родителя. Главное: коммит нельзя изменить, он «высечен в камне». Это пригодится, когда дойдём до rebase.

Ветка — это просто имя, прикреплённое к последнему коммиту. Представь стикер с надписью main, приклеенный к коммиту. Ветка — не папка и не копия файлов, поэтому создаётся мгновенно.

HEAD — метка «Вы находитесь здесь», как на карте в торговом центре. Обычно HEAD указывает на ветку, а ветка — на коммит: HEAD → ветка → коммит.

Как читать двойные схемы

Каждая схема в конспекте нарисована дважды. Слева — граф веток: так историю показывают Visual Studio и другие программы. Линии — ветки, кружки — коммиты. Справа — те же коммиты «изнутри»: видно, к какому коммиту приклеен стикер каждой ветки и где стоит HEAD. Смотри сначала на граф, а потом на стикеры.

Коммит в main
Коммит в bugfix
Merge-коммит (два родителя)
HEAD — «ты здесь»
Стикер ветки (куда она указывает)

Пройди пять шагов кнопками под схемой или нажми ▶, чтобы проиграть их подряд.

Правило коммита

Новый коммит всегда пристраивается туда, где стоит HEAD, и двигает вперёд только ту ветку, на которую смотрит HEAD.

Теперь в main есть D, которого нет в bugfix, а в bugfix — E, которого нет в main. Как их соединить? Есть два способа: merge и rebase. Чтобы увидеть такую развилку у себя, выполни git log --oneline --graph --all — Git нарисует ту же картинку символами (как её читать — в разделе 10).

РАЗДЕЛ 03

Главное правило, которое нужно выучить наизусть

Главное правило

Git меняет только ту ветку, на которой ты стоишь.

Ветка, которую ты называешь в команде, — источник изменений. Её Git не трогает. Это то же правило, что и с коммитом: двигается только ветка под HEAD.

1Встань, куда нужноgit switch <ветка, которую меняем>
2Назови другую веткуgit merge <откуда> или git rebase <на что>
КомандаГде стоишьКак читать вслухЧто меняетсяЧто не меняется
git merge bugfixв main«Влей bugfix в меня»mainbugfix
git rebase mainв bugfix«Пересади меня на верхушку main»bugfixmain
Частая ошибка

Выполнить команду не в той ветке. Перед merge или rebase всегда проверяй, где стоишь:

  • в Git Bash имя ветки видно в скобках в подсказке: ~/report (main);
  • git status пишет в первой строке On branch main;
  • в Visual Studio текущая ветка показана в строке состояния внизу окна.
РАЗДЕЛ 04

Merge (слияние): два сценария

git merge добавляет работу другой ветки в твою текущую. Git сам выбирает один из двух способов. Выбирать не нужно, но важно понимать, что произошло.

4.1. Fast-forward — «перемотка вперёд»

Ситуация: ты создал ветку bugfix и сделал в ней коммит D. А в main за это время никто ничего не коммитил.

Git видит, что main можно просто «догнать»: D уже стоит сразу после C. Поэтому новый коммит не создаётся — Git передвигает стикер main вперёд на D. Как перемотка видео — отсюда и название. В терминале это выглядит так (хеши у тебя будут другими):

$ git merge bugfix
Updating f600372..8e3f1b4
Fast-forward
 doc.txt | 1 +
 1 file changed, 1 insertion(+)
Аналогия с Word

Боря ничего не менял в своей копии, а Аня дописала текст. Склеивать нечего: Боря просто берёт последнюю версию Ани.

Для любопытных

Чтобы Git всегда создавал узел слияния, даже когда можно перемотать, есть флаг git merge --no-ff bugfix.

4.2. Настоящее слияние — merge-коммит

Ситуация как в конце раздела 2: main ушла вперёд (коммит D), bugfix тоже (коммиты E и F). Просто «перемотать» уже не получится — у веток разная история.

Git создаёт новый особый коммит M — merge-коммит (коммит слияния). У обычного коммита один родитель, а у M их два: D и F. Он как узел, который связывает две линии истории, и в нём есть всё: и изменения из D, и из E и F. main сдвинулась на M, а bugfix осталась на F — Git её не трогал. Это и есть главное правило из раздела 3.

$ git merge bugfix
Auto-merging doc.txt
Merge made by the 'ort' strategy.
 doc.txt | 1 +
 1 file changed, 1 insertion(+)

Не пугайся слова 'ort' — это просто название алгоритма слияния внутри Git.

Почему это называют «трёхсторонним слиянием»

Git сравнивает не две версии, а три: общего предка C, верхушку main (D) и верхушку bugfix (F). Сравнивая каждую ветку с предком, Git точно знает, кто что изменил:

  • изменил только один — берётся его вариант;
  • изменили оба, но в разных местах — берутся оба изменения;
  • изменили оба одно и то же место по-разному — конфликт (раздел 5).
Аналогия с Word

Аня и Боря садятся вместе, кладут рядом оригинал и две свои копии и собирают итоговый документ. Новая версия «Отчёт (объединённый)» — это и есть merge-коммит.

4.3. После слияния: убираем стикер

Работа из bugfix уже в main, ветка больше не нужна:

$ git branch -d bugfix
Deleted branch bugfix (was 551db31).

Удаляется только стикер — коммиты E и F остаются в истории main. Флаг -d безопасный: если ветка ещё не слита, Git откажется её удалять и напишет error: the branch 'bugfix' is not fully merged.

РАЗДЕЛ 05

Конфликт при слиянии: не поломка, а вопрос

Конфликт возникает, когда обе ветки изменили одни и те же строки одного файла по-разному. Git не умеет угадывать, чей вариант правильный, и честно спрашивает тебя. Ничего не сломалось: Git просто остановился и ждёт решения.

Аналогия с Word

Аня переименовала заголовок в «Annual Report», а Боря — в «Final Report». Какой оставить? Решить может только человек.

Как выглядит конфликт

$ git merge anya-title
Auto-merging doc.txt
CONFLICT (content): Merge conflict in doc.txt
Automatic merge failed; fix conflicts and then commit the result.
::br main|MERGING
$ git status
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
        both modified:   doc.txt

Подсказка Git Bash сменилась на (main|MERGING): «идёт слияние, оно ещё не закончено». А git status в любой непонятной ситуации пишет, что происходит и что делать дальше. Перевод подсказок: «исправь конфликты и выполни git commit» или «выполни git merge --abort, чтобы отменить слияние». Строка both modified значит «изменён в обеих ветках» — вот он, файл с конфликтом.

Внутрь файла Git вставил специальные маркеры:

doc.txt конфликт
1<<<<<<< HEADначало: версия из твоей ветки
2Final Report
3=======забор между версиями
4Annual Report
5>>>>>>> anya-titleконец: версия из вливаемой ветки
6Paragraph 1
7Lorem ipsum (Anya)
8Paragraph 2
МаркерЧто значитКак запомнить
<<<<<<< HEADНачало версии из текущей ветки (где ты стоишь)Верх — «моё, здесь»
=======Разделитель между двумя версиямиЗабор между соседями
>>>>>>> anya-titleКонец версии из вливаемой веткиНиз — «пришло оттуда»

Реши конфликт сам: попробуй прямо здесь

Что оставить в заголовке?

doc.txt конфликт

Выбери вариант — и увидишь, как будет выглядеть файл без маркеров.

Решение за 4 шага

  1. Открой файл с конфликтом, например notepad doc.txt.
  2. Реши, что оставить: верхний вариант, нижний, оба или свой собственный. Например, Final Annual Report.
  3. Удали все три строки-маркера (<<<<<<<, =======, >>>>>>>) и сохрани файл.
  4. Скажи Git, что конфликт решён, и заверши слияние коммитом.
$ git add doc.txt
$ git commit -m "Merge anya-title: resolve title conflict"
[main a2a66d5] Merge anya-title: resolve title conflict
::br main

Здесь git add означает «я разобрался с этим файлом». После коммита появится обычный merge-коммит, а подсказка снова станет просто (main).

Если запутался

Всегда есть кнопка отмены — git merge --abort. Всё вернётся к состоянию до слияния, как будто ты ничего не начинал.

РАЗДЕЛ 06

Rebase (перебазирование): пересадка ветки

git rebase решает ту же задачу, что и merge, — соединяет работу двух веток. Но вместо узла-склейки он переносит твои коммиты на верхушку другой ветки. История получается такой, будто ты начал работу уже после всех изменений в main.

Аналогия с Word

Боря говорит Ане: «Дай мне свою последнюю версию. Я возьму её за основу и заново внесу туда свои правки — по порядку, одну за другой». В итоге кажется, что Боря начал работать после Ани, хотя на самом деле они работали одновременно.

Та же развилка, что в разделе 4.2, но теперь мы стоим в bugfix. Пройди шаги: второй и третий показывают, что происходит внутри одной команды git rebase main.

Что делает Git — по шагам

  1. Находит общего предка двух веток — коммит C.
  2. Запоминает, что изменили твои коммиты E и F, и временно откладывает их в сторону.
  3. Переставляет bugfix на верхушку main — коммит D.
  4. Заново применяет изменения по одному: сначала из E — получается новый коммит E′, потом из F — новый коммит F′.
  5. Передвигает стикер bugfix на F′.
$ git rebase main
Successfully rebased and updated refs/heads/bugfix.

Почему E′, а не E? Самое важное про rebase

Помнишь, что коммит нельзя изменить? В каждом коммите записан его родитель. У E родителем был C, а теперь должен стать D. Значит, это уже другой коммит: с тем же сообщением и теми же изменениями, но с новым хешем.

Запомни

Rebase не передвигает коммиты, а создаёт их копии. Штрих в E′ и означает «копия E».

Это видно в терминале: сообщения те же, а хеши новые.

Сообщение коммитаХеш до rebaseХеш после rebase
Anya: add footerb7e86c3e427cf5
Anya: add ending21e76bd8544538

А старые E и F? Они не исчезают мгновенно, но на них больше не указывает ни одна ветка. В обычном графе их уже не видно, а со временем Git уберёт их сам.

Завершаем: быстрое слияние

Rebase обновил только bugfix (главное правило!), main всё ещё стоит на D. Чтобы работа попала в main, переходим туда и сливаем — это последний шаг на схеме выше:

$ git switch main
Switched to branch 'main'
::br main
$ git merge bugfix
Updating c3445d8..8544538
Fast-forward
 doc.txt | 2 ++
 1 file changed, 2 insertions(+)

bugfix растёт прямо из верхушки main, поэтому Git делает fast-forward. Итог: история — одна прямая линия, без развилок и merge-коммитов. В этом и есть главный плюс связки «rebase + merge».

РАЗДЕЛ 07

Конфликт при rebase

Причина та же, что и при merge: две ветки изменили одни и те же строки. Маркеры в файле тоже те же. Но есть три отличия, которые нужно знать.

Отличие 1. Конфликт может появиться несколько раз

Rebase переносит коммиты по одному. Если конфликтуют несколько коммитов, Git остановится на каждом. Подсказка Git Bash показывает прогресс: (bugfix|REBASE 1/2) — «переношу 1-й коммит из 2». Сообщение длинное, но в нём уже есть вся инструкция:

$ git rebase main
Auto-merging doc.txt
CONFLICT (content): Merge conflict in doc.txt
error: could not apply 217b719... Anya: check paragraph 2
hint: Resolve all conflicts manually, mark them as resolved with
hint: "git add/rm <conflicted_files>", then run "git rebase --continue".
hint: You can instead skip this commit: run "git rebase --skip".
hint: To abort and get back to the state before "git rebase", run "git rebase --abort".
Could not apply 217b719... Anya: check paragraph 2
::br anya-p2|REBASE 1/1

Перевод: «Реши конфликты вручную, отметь их через git add и выполни git rebase --continue. Можно пропустить этот коммит через --skip. Чтобы всё отменить — --abort».

Отличие 2. Завершение — другой командой

После решения конфликта git commit не нужен. Вместо него:

$ git add doc.txt
$ git rebase --continue
[detached HEAD 6ace489] Anya: check paragraph 2
 1 file changed, 1 insertion(+), 1 deletion(-)
Successfully rebased and updated refs/heads/anya-p2.
::br anya-p2

Git сам создаст исправленную копию коммита и перейдёт к следующему. Перед этим он может открыть редактор с сообщением коммита — просто сохрани и закрой его (в Vim: Esc, :wq, Enter).

Отличие 3. «Моё» и «чужое» меняются местами

Во время rebase Git встаёт на main и по очереди добавляет твои коммиты сверху. Поэтому верхняя часть (HEAD) — это версия из main, а нижняя — твой переносимый коммит:

doc.txt конфликт при rebase
4<<<<<<< HEADэто main — новая база
5Paragraph 2 (checked by Borya)
6=======
7Paragraph 2 (checked by Anya)
8>>>>>>> 217b719 (Anya: check paragraph 2)это твой коммит

Это путает даже опытных разработчиков. Не угадывай, где чьё, — читай сам текст в каждой части. Подсказка: после >>>>>>> Git пишет хеш и сообщение твоего коммита, по ним легко узнать свою часть.

Три выхода из остановленного rebase

КомандаЧто делаетКогда нужна
git rebase --continue«Я решил конфликт, продолжай»После исправления файла и git add
git rebase --abortОтменить всё: ветка станет как до rebaseЗапутался или передумал
git rebase --skipВыбросить этот коммит и идти дальшеРедко. Осторожно: изменения этого коммита пропадут

Во время rebase Git может написать detached HEAD. Это нормально: пока идёт перенос, HEAD временно указывает прямо на коммит, а не на ветку. После завершения rebase всё вернётся на место.

РАЗДЕЛ 08

Золотое правило rebase

Нельзя

Не делай rebase коммитов, которые уже отправлены в общий репозиторий (git push) и которыми пользуются другие.

В книге Pro Git это звучит так: «Не перемещайте коммиты, уже отправленные в публичный репозиторий».

Почему это опасно:

  1. Rebase заменяет твои коммиты копиями с новыми хешами (раздел 6).
  2. У коллег остались старые коммиты, и они уже могли построить на них свою работу.
  3. Когда вы снова обменяетесь работой, Git увидит две разные истории. Одни и те же изменения окажутся в двух экземплярах.
  4. Чтобы отправить переписанную историю, придётся делать принудительный push. Им легко стереть чужую работу.
Аналогия

Нельзя переписывать страницы книги, которую уже раздали читателям. У них на руках старое издание, и страницы у вас перестанут совпадать.

КоммитыМожно rebase?
Только на твоём компьютере, ещё никому не отправленыДа
Отправлены в общий репозиторий, с ними работают другиеНет — только merge
Не уверенНет — только merge

Merge в этом смысле всегда безопасен: он только добавляет новые коммиты и никогда не переписывает старые.

РАЗДЕЛ 09

Merge или rebase: в чём разница

Обе команды дают одинаковые файлы в итоге. Разница только в том, как выглядит история.

Merge — черновик

Сшивает две ветки узлом. История честная: видно, что работа шла параллельно и когда её соединили. Как черновик, где видны все линии рассуждений.

Rebase — чистовик

Переписывает твои коммиты так, будто ты работал последовательно. История аккуратная, в одну линию, но часть правды о том, «как было», теряется.

Один и тот же старт — два разных результата. Переключай вкладки под схемой:

Что выбрать новичку

  • Не уверен — делай merge. Он никогда не переписывает историю.
  • Rebase — удобный способ «подтянуть» свежий main в свою личную ветку, пока она есть только у тебя.
  • Ни одна команда не «лучше» другой. Команды разработчиков заранее договариваются, как работать, — следуй правилу своей команды.

Типичный сценарий работы над задачей

  1. git switch -c feature — создать ветку под задачу и сразу перейти в неё.
  2. Работать и делать коммиты.
  3. Если main за это время ушла вперёд — подтянуть её в свою ветку: git rebase main (если ветка только твоя) или git merge main (если ветка общая).
  4. Задача готова — git switch main, затем git merge feature.
  5. git branch -d feature — убрать стикер.

То же самое в Visual Studio

Visual Studio выполняет те же команды Git, только через кнопки и меню. Главное правило здесь то же: сначала встань в нужную ветку, потом выбери действие с другой веткой.

Названия пунктов даны для английского интерфейса Visual Studio 2022; в Visual Studio 2026 Git-инструменты устроены так же. Окна ниже — упрощённые схемы, а не скриншоты.

11.2. Ветки: создать, перейти, закоммитить

Создать ветку: Git → New Branch. В окне Create a new branch введи имя (Branch name: bugfix), в поле Based on выбери main, оставь галочку Checkout branch и нажми Create.

  • С галочкой Checkout branch это git switch -c bugfix — создать и сразу перейти.
  • Без галочки это git branch bugfix — только приклеить стикер.
  • Другой путь: в окне Git Repository правый клик по main → New Local Branch From.

Перейти в ветку (git switch main): дважды щёлкни по ветке в списке Branches окна Git Repository или выбери её в переключателе в строке состояния. Текущая ветка в списке выделена жирным.

Сделать коммит (git commit -am): в окне Git Changes напиши сообщение и нажми Commit All.

11.3. Граф веток

Граф живёт в окне Git Repository, справа от списка веток. Это та же картинка, что и git tree, только в цвете. Он делится на три части: Incoming — коммиты коллег на сервере, которых у тебя ещё нет; Outgoing — твои коммиты, ещё не отправленные на сервер; Local History — вся остальная история.

Как увидеть несколько веток сразу. По умолчанию видна история одной ветки. Наведи мышь на ветку в списке — появится значок глаза (Toggle Branch in History). Включи его для main и для bugfix: линии веток раскрасятся в разные цвета, рядом с коммитами появятся ярлыки веток. Эта функция есть начиная с Visual Studio 2022 версии 17.7.

  • каждая строка — один коммит, свежие сверху (как в git tree);
  • точка на цветной линии — коммит этой ветки; линия раздваивается — развилка;
  • две линии сходятся в одну точку — merge-коммит;
  • ярлыки с именами — стикеры веток, как (main) в терминале;
  • щелчок по коммиту открывает детали: сообщение, автора и изменённые файлы.
Кнопка Show First Parent Only

Она на панели над графом и прячет боковые ветки. Пока учишься, держи её выключенной, иначе развилок не будет видно.

Merge в Visual Studio

  1. В окне Git Repository дважды щёлкни по main — ты встал в main (git switch main).
  2. Правый клик по bugfix → Merge 'bugfix' into 'main' (git merge bugfix).
  3. Если Visual Studio попросит подтвердить — согласись.
  4. Посмотри на граф. При fast-forward main просто сдвинется. При настоящем слиянии появится точка, в которую сходятся две линии.

Rebase в Visual Studio

  1. Дважды щёлкни по bugfix (git switch bugfix).
  2. Правый клик по main → Rebase 'bugfix' onto 'main' (git rebase main) — «пересадить bugfix на main».
  3. На графе коммиты bugfix встанут после последнего коммита main, в одну линию.
  4. Чтобы работа попала в main: двойной клик по main, правый клик по bugfix → Merge 'bugfix' into 'main'. Будет fast-forward.
Правило для Visual Studio

Двойной клик — куда встать. Правый клик — по другой ветке. В терминале то же самое: git switch — куда встать, а в команде merge или rebase — другая ветка.

11.5. Конфликты в Visual Studio: Merge Editor

  1. Visual Studio сообщит, что слияние или rebase остановлено из-за конфликтов. В окне Git Changes появится раздел Unmerged Changes со списком файлов.
  2. Дважды щёлкни по файлу (или правый клик → Open Merge Editor). Откроется Merge Editor с тремя панелями:
    • Incoming — версия из вливаемой ветки (в терминале это часть ниже =======);
    • Current — версия из ветки, где ты стоишь (часть под <<<<<<< HEAD);
    • Result — итог, который попадёт в файл.
  3. Отметь галочками нужные строки. Можно взять всё с одной стороны кнопками Take Incoming (F10) или Take Current (F11) либо дописать текст вручную в Result.
  4. Нажми Accept Merge — это то же, что сохранить файл и сделать git add.
  5. Заверши операцию в окне Git Changes: при merge введи сообщение и нажми Commit Staged (git commit), при rebase нажми Continue (git rebase --continue).
  6. Передумал — нажми Abort (--abort), и всё вернётся как было.

Попробуй на схеме Merge Editor — тот же конфликт с заголовком, что в разделе 5:

РАЗДЕЛ 12

Шпаргалка

Три правила, которые спасают от страха, и все команды раздела на одной странице. Нажми на карточку, чтобы скопировать команду.

1Git меняет только ветку, на которой ты стоишь

Сначала git switch, потом merge или rebase.

2Конфликт — не поломка, а вопрос

И у него всегда есть кнопка отмены: --abort.

3Rebase — только для своих неопубликованных коммитов

Не уверен — делай merge.

Словарик

Слияние (merge)
Добавить работу другой ветки в текущую.
Перебазирование (rebase)
Перенести свои коммиты на верхушку другой ветки, то есть создать их копии.
Fast-forward (перемотка вперёд)
Слияние без нового коммита: ветка просто сдвигается вперёд.
Merge-коммит
Коммит с двумя родителями — «узел» слияния.
Трёхстороннее слияние
Сравнение трёх версий: общего предка и двух верхушек веток.
Общий предок
Последний коммит, который есть в обеих ветках, — точка развилки.
Конфликт
Обе ветки изменили одно место по-разному, и Git просит выбрать.
Маркеры конфликта
Строки <<<<<<<, =======, >>>>>>>, которые Git вставляет в файл.
HEAD
Метка «Вы находитесь здесь». Обычно указывает на текущую ветку.
Detached HEAD
HEAD указывает прямо на коммит, а не на ветку. Временно бывает во время rebase.
Current / Incoming
В Visual Studio: версия текущей ветки / версия из вливаемой ветки.
Стикер ветки
Наш образ ветки: имя, приклеенное к коммиту, которое двигается вперёд при новых коммитах.
